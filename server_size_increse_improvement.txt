Technical Improvement Proposal: Rethink Data & Performance
Based on our recent work with the 100MB backup limit and auto-sync, I've identified several high-impact technical improvements to make the system more robust as your data grows.

1. Zero-Compression to Gzip (Data Efficiency)
Currently, backups are raw JSON text. As you approach 100MB, this consumes significant storage and bandwidth.

Improvement: Switch to .json.gz or .zip format.
Benefit: Reduces a 100MB file to roughly 10–15MB. This makes cloud syncing much faster and saves OneDrive/Google Drive space.
2. Chunked Data Processing (Reliability)
Importing or exporting 100MB in a single PHP request is risky; it can hit memory limits or time out if the server is slow.

Improvement: Implement "Batching." Instead of one big request, the browser fetches data table-by-table or in slices of 1,000 rows.
Benefit: Zero risk of timeouts or "Out of Memory" errors, no matter how large your database becomes.
3. Automated Database Maintenance (Performance)
The activity_log and performance tables grow with every click. Over time, this slows down dashboard queries.

Improvement: Add a "Maintenance Task" that archives or deletes logs older than 90 days.
Benefit: Keeps the database lean, ensuring the dashboard remains "snappy" even after years of use.
4. Backup Integrity Checksums (Safety)
Cloud sync (like OneDrive) can sometimes have sync conflicts that result in a partial or corrupted file.

Improvement: Add a checksum (SHA-256 hash) to the backup metadata.
Benefit: The system will verify the file is 100% perfect before attempting to restore, preventing "half-finished" imports that could break data consistency.
Which of these would you like to prioritize? I can start with the Gzip Compression (1) or Batch Processing (2) as they provide the most immediate benefit for large backups.
